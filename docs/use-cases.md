# Use Cases — What CacheFlow Is For

CacheFlow targets a single set of pain points across its runtime. This document explains the user problem, what CacheFlow coordinates, what the model / tools / AKV / serving system do, expected outputs, and limitations.

## 1. Repository analysis and bug investigation

**User problem:** Long-running agents accumulate large trajectories as they inspect files, build import maps, trace dependencies, and formulate hypotheses. Over time, repeated inspection of overlapping subgraphs is wasted work, and stale prompt content inflates inference cost.

**What CacheFlow coordinates:**
- A deterministic DAG that enumerates investigation subgraphs up front from validated inputs. The LLM cannot dynamically modify the graph structure at runtime.
- Deterministic file tools (`grep`, `read_file`, `list_dir`, `symbol_map`) that produce byte-stable output for identical fixtures.
- An AKV cache controller that drops eligible scratch entries beyond the retention window and repositions retained entries at fixed turn intervals. Verdict evidence and cross-check conclusions are marked as protected so they survive cleanup.

**What the model does:** Reports whether findings are `reachable`, `not_reachable`, or `needs_human`.

**What tools do:** Inspect repository contents deterministically.

**What AKV does:** Executes explicit `drop_message` and `reposition` fields for cache policy effects, and records usage metrics.

**Outputs:**
- `report.md`
- `report.json`
- `trace.jsonl`

**Limitations:** VulnTriage demo is CPU-only offline. Live AKV verification pending hardware.

## 2. Database and ETL incident investigation

**User problem:** Production SQL pipelines emit timestamps that are out of order, batch watermarks drift from actual data, and row counts disagree after a regression. Investigation requires inspecting models, logs, watermarks, and join behavior, but direct production access must not be the default.

**What CacheFlow coordinates:**
- A placeholder workflow (`examples/db_incident/workflow.py`) documents the required interface contract. When implemented, it will accept an explicitly configured read-only connection spec and produce investigation artifacts without touching production infrastructure.

**What the model does:** Formulates timeline, impact quantification, root-cause hypotheses, verification queries, and regression suggestions.

**What AKV does:** Used for conversational reasoning about ETL incidents, not for direct SQL access.

**Outputs:** Investigation artifacts and evidence documents.

**Limitations:** Connector plug-in is experimental and not yet wired into the CLI. Do not attempt to point `analyze-db` at an unauthenticated production endpoint.

## 3. Long-running tool-using AI workflows

**User problem:** Interactive sessions that coordinate dependent tasks may be interrupted mid-execution. Repeating the entire trajectory is wasteful; users want a validated resume path from arbitrary boundaries.

**What CacheFlow coordinates:**
- Checkpoint boundaries after each node, each investigation substep, each validated verdict submission, and report rendering.
- Atomic checkpoint writes with schema versioning and integrity checksums.
- A resume procedure that restores message history, cache-operation history, and tool execution ledger, then continues only from the last valid completed boundary.
- A duplicate-side-effect prevention mechanism that records canonicalized tool calls and reuses recorded results instead of repeating completed work.

**Outputs:**
- `latest.json` checkpoints at each boundary
- Full trace history at any resume point

**Limitations:** Resume preserves logical correctness but cannot guarantee a restored GPU KV cache. If the serving process restarts, recomputed context is needed; state restores to client state only.

## 4. Inference and KV-cache policy evaluation

**User problem:** Users want to compare how different cache policies affect inference latency, token counts, and available memory. They need measured cache operations, not simulated ones.

**What CacheFlow coordinates:**
- Two baseline modes: B0 (no CacheFlow-scheduled operations), B2 (integrating CacheFlow's protected-message rules, node-scoped cleanup, and checkpoint instrumentation).
- Three benchmark families: synthetic trajectories (A), VulnTriage fixtures (B), recovery workloads (C).
- Per-run metrics files (`metrics.json`, `trace.jsonl`) plus CSV aggregation across multiple repetitions.

**Outputs:**
- `results/metrics.json`, `results/trace.jsonl`, `results/report.md`
- CSV aggregates in `results/aggregate.csv`

**Limitations:** Run A0–A2 require live AKV/SGLang hardware. Sample values are illustrative unless generated by an actual run.
